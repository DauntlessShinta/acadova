## Analytics definitions

All filtered endpoints accept `from=YYYY-MM-DD&to=YYYY-MM-DD`, both required together, maximum 366 inclusive days. Matching uses `[from at 00:00 UTC, day after to at 00:00 UTC)`. Invalid dates, reversed/excessive windows and unknown query fields return 400. Existing calls without dates remain all-time. Undated historical rows cannot be attributed to a date window and are excluded from filtered results; no dates are backfilled. Endpoint access requires a database-authorized, eligible Administrator.

| Function | Source / calculation |
| --- | --- |
| Tutoring demand and activity | `Session.createdAt`: request count, current stored status of that creation cohort, daily request counts, top 20 exact stored subjects by count. Status aliases are not double-counted. Stored historical completion alone is not settlement evidence. |
| Credit movement and payment activity | `CreditTransaction.createdAt`: event counts and stored amount sums grouped by type and adjustment direction. `session_payment` rows count once per ledger record, not once per participant. Daily payment events use ledger dates. Starting grants, assessment rewards, learning spending and Admin credits/debits remain separate. Totals are movements of internal credits, not cash, current balances, net credit supply or verified provider attendance. |
| Learning engagement and outcomes | `AssessmentAttempt.submittedAt`: official count/passed count, `passed / official count × 100` rounded to one decimal, average stored official score; explicit practice excluded. Missing historical mode is official. Repeat attempts count separately. `StudyAttempt.submittedAt` counts submitted free quizzes only; `LearningUnlock.unlockedAt` counts persisted paid resource/module entitlements, not content views. Empty pass-rate denominators return null. |
| Visible reputation | `Rating.createdAt`, hidden reviews excluded: average, count and star distribution. Empty results are unrated; User rating defaults are never substituted. |

Five KPIs: visible review average, tutoring credits transferred, requests created, official assessment pass rate, learning unlocks. Charts: UTC request/payment line trend, credit-source horizontal bars, learning-activity horizontal bars; existing subject demand and rating distribution remain. The period affects every KPI and chart. Daily data has a keyboard-operable table alternative; comparisons expose exact values in text. Presets cover 7/30/90 days; custom windows and browser URL/history are supported. Stale responses cannot overwrite a newer analytics period. Unavailable sources never become fabricated zeros.

Insights identify leading recorded subject demand, the current awaiting-confirmation/dispute cohort, and observed official attempt outcomes. They support coverage and content review decisions without labelling behavior as fraud or claiming attendance verification.

Data pipeline: user actions → validated/authorized Express controllers → Mongoose records (transactional/idempotent business writes where required) → MongoDB timestamp matching/grouping/facets → protected aggregate APIs → React KPIs, charts and exact values. Analytics is read-only and does not invoke settlement or award credits.

## Scalability limits and next steps

MongoDB performs grouping; Node receives bounded summaries, top 20 subjects and at most 366 daily buckets. Queries use an 8-second server execution limit. This bounds response size, **not** scan work or measured capacity. No 10×/100× load benchmark was run.

- At 10×: use representative synthetic volume, measure latency/concurrency, and review `explain("executionStats")` for timestamp filters. Consider operator-approved performance indexes on Session/CreditTransaction/Rating `createdAt`, AssessmentAttempt/StudyAttempt `submittedAt`, and LearningUnlock `unlockedAt`; choose compound definitions from measured predicates. No performance indexes were created or added to schema auto-indexing.
- At 100×: benchmark again; consider daily aggregate rollups, bounded cache freshness and cursor pagination for record directories. Define correction/reconciliation and rebuild policies before relying on rollups. These optimizations are **not implemented**. Existing User/Session directories still download their records and filter locally; they are not claimed to scale indefinitely. Staff queues are capped by existing APIs, and recent credit filtering covers the loaded 50 events only.
- Production correctness indexes remain separate requirements under the existing rollout guides. A schema declaration or small local test does not prove the live index definition.
